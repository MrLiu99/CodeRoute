# 项目盘点与重新规划（2026-09-29）

> 这是重新规划时的状态快照。后续执行进度与当前版本结果见 [固定版本交付评测](../RELEASE_EVALUATION.md)，下方“未完成”等描述对应盘点时点。

本报告只核查原始需求、当前源码和既有运行记录，没有新增模型实验。当前定位：架构完整、能真实演示的研究原型；尚未完成最新版本统一回归，复杂修复稳定性与动态路由收益未得到证明。

## 原始范围与实际进度

原始目标为小型 Python + pytest 修复系统，10～20 个自建案例，不训练模型、不做大型真实仓库、不做 GUI。当前共有 14 个不同案例，数量符合原计划；120 项工程自动化测试不是 120 个修复案例。

| 目标 | 当前状态 | 证据与限制 |
|---|---|---|
| 输入仓库/issue、读代码、改源码、执行测试、输出 diff | 已实现并真实跑通 | 在副本修改，不自动回写原仓库 |
| 五角色、共享状态、角色上下文、执行循环 | 已实现 | Tester 确定性执行 pytest，其余角色调用模型 |
| Fixed、LLM、规则+LLM、Hybrid | 已实现并实际运行 | 实现了不同策略，不等于已证明 Hybrid 更好 |
| 规则→轻量→主模型回退 | 已接入真实服务 | DeepSeek 主模型、OpenRouter Qwen 路由；没有 Jev 或本地模型 |
| Tester→Debugger→Developer 闭环 | 有真实完整成功记录 | 上轮流式 hybrid 修复后公开测试 7/7、独立验收 13/13 |
| Reviewer→Developer 动态返回 | 有真实执行记录 | 最新流式 hybrid 出现该路径，但整次运行失败 |
| 日志、token、耗时、步骤、模型/路由记录 | 已实现 | 保存失败，不用事后补丁通过冒充流程成功 |
| 工程验证 | 最新完整套件 120 项通过 | 验证系统机制，不代表任意 bug 修复能力 |
| 评测与交付 | 部分完成 | 历史有四策略比较；最新版本没有全量统一成绩 |

基本流程可运行：分析→修改→测试→失败诊断/重修→审查→输出。动态分支并非只存在于模拟中。但复杂运行仍可能因动作协议、无效编辑、上下文或调用预算耗尽而中断；“跑通过”不等于“稳定通顺”。

## 已处理的问题与仍未解决的问题

已实现：正式工具调用及调用 ID 续接；空响应/截断分类与有界纠正；真实源码上下文；批量编辑与未验证修改交接；当前 revision 测试/审查门禁；原文需求覆盖和引用存在性检查；独立验收、完整失败轨迹和用量统计。部分机制只有工程测试覆盖，例如本轮最后两次没有触发开发预算交接，不能声称有真实成功收益。

复杂案例存在多类原因，不能只归因于模型或预算：

1. 补丁逻辑错误：跨块转义引号、BOM 去除、闭引号后非法字符等边界曾漏修。流式解析需要在多个输入片段之间保持正确状态。
2. 公开测试与审查不充分：公开测试通过、Reviewer 接受，独立验收仍可能失败。需求编号齐全、引用存在不能证明推理正确。
3. 动作协议与编辑效率：历史出现空正文、非法 JSON、多工具响应；新模式仍出现多函数请求、替换旧片段不匹配、无效编辑。机制改善不代表问题消失。
4. 模型生成测试错误：本轮曾出现必然失败的诊断断言。保留错误测试可能阻塞正确补丁；当前没有可靠的错误测试裁定流程。
5. 预算是最后停止原因，未必是根因：最新 dynamic 64 次调用耗尽；hybrid 52 次调用后达到本地上下文上限；两份最终补丁均未通过独立验收。反复读改、错误断言和重复诊断消耗预算。
6. 评测本身的限制：全部为小型自建案例；转账案例有规格歧义；没有最新版本全量回归，没有足够证据说明路由相对固定流程提高成功率或降低总成本。模型自报置信度未校准。

工程边界：只处理依赖就绪、可信 Python 仓库，不能创建源码文件或改测试/配置，不自动安装依赖；副本不是操作系统沙箱。这些限制部分属于第一版范围，并非都需要补齐。

## 重新规划

此前工作偏离之处：在同一个复杂案例上反复迭代；新增原计划明确暂不做的自动生成测试；修改版本间的结果未及时形成统一现状表。后续回到原始可演示 MVP，停止不断增加机制。

以下是拟定计划，尚未执行新实验：

1. 收敛范围并离线修正：以原生调用、五角色、动态路由、公开测试和文字审查为第一版主线；生成测试保留为可选实验功能，不作为第一版必选能力。独立验收不移除、不放宽。核对无效编辑和上下文增长，并把转账规格修正保存为新案例版本，旧成绩不覆盖。
2. 冻结代码与配置，统一回归：先 Hybrid 在 14 个案例各运行一次，最多 14 次，不因失败挑选重跑；逐例列出最终结果、退出阶段、失败原因、调用量。此阶段才建立当前版本成绩。
3. 核对原始动态行为验收：验证成功修复闭环、真实失败恢复、Reviewer 返回修改、真实轻量调用与回退；缺少的证据明确列出，不能以强制模型犯错制造成功。
4. 在上述结果可解释后决定是否做新版策略对照：同一批案例、同一预算与代码比较固定/LLM/Hybrid；不预设 Hybrid 必须赢，不自动扩大实验。若比较四策略则完整批次为 56 次，应另定调用总额。
5. 完成交付：统一 README、架构、逐案例结果、代表性成功/失败轨迹与已知限制。可演示原型的完成标准是流程真实、结果可复现且报告一致，不要求复杂案例全成功；若目标升级为可靠修复服务，则需另行约定成功率、独立新案例与更广泛验证标准。

现在不扩大测试集、不更换模型、不追加模型调用。第一优先级是明确且稳定的第一版范围与一份可信的最新成绩单。
