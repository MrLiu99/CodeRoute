# 结构化调用与补充验证改造

本轮针对旧验收 1/8 的三类问题：动作 JSON 格式不稳定、重复读取消耗回合、审查引用存在但语义判断错误。旧结果不覆盖。

## 实现

- 新配置 `configs/reliable-tools.json` 开启 `native_tool_calls`、`protocol_recovery` 和 `review_validation`。模型与上轮验收一致，仍为 8192 输出 token、12 个角色回合、64 次总调用、16 个步骤、600 秒。
- 多角色通过 Chat Completions 的 `tools` 提交动作，路由只调用 `route(choice, confidence, reason)`。工具参数仍由本地权限、schema、需求和 revision 门禁检查，不信任提供商格式保证。
- 正式保存 `tool_call_id` 并用 `role=tool` 返回结果；截断响应不执行。主模型空响应、动作 JSON 语法错误或意外的多函数调用，每角色合计最多纠正一次，仍占原角色回合和总调用预算，第二次失败停止。多函数响应中的任何动作都不执行，每个 ID 都收到未执行反馈，避免下一轮协议不完整。HTTP 错误不自动重试；轻量异常仍在预算内回退。
- 各角色获得有界的当前源码与测试片段，不再强迫每个角色重复读同一批文件。
- Developer 支持 `apply_edits`：一次提交多处修改，全部路径与旧片段先校验，通过后才写入；同一文件的多处替换按顺序执行，写入错误时尝试恢复原内容。不能编辑测试或配置，不增加模型权限。
- `developer_budget_handoff` 开启后，Developer 用完单角色回合但已改变源码，会将该未验证 revision 交给 Tester。它不代表提交成功或测试通过，不增加全局模型调用、步骤或时间预算；没有修改或全局预算耗尽时仍停止。
- Reviewer 可调用 `run_review_test(requirement_ids, reason, code)`。在独立副本中执行其编写的 pytest 补充测试，结果包含日志、源码 revision 和对应需求编号；不使用外部验收测试生成这些检查。
- 开启补充验证时，Reviewer 接受必须满足当前 revision 的补充测试通过。每次运行最多保存三份补充测试；已提交测试全部保留，新增更弱测试不能掩盖先前失败。代码改变后自动重跑全部既有补充测试。
- 不改变原仓库与修复工作区的测试。每份补充测试限制为 1–3 个聚焦函数，语法错误在执行前拒绝；若测试本身的语义错误，应报告测试问题，不能删除该失败记录或为了测试改变明确需求。Reviewer 在已有失败结果时仍申请接受，会被明确改判为拒绝，并交给 Analyzer 重新核对程序和测试，避免反复提交直到上下文耗尽。

补充测试在副本中执行，但不是操作系统安全沙箱，仍限可信小型仓库；引用齐全和生成测试通过都不构成形式化正确性证明。独立验收仍决定最终成功。

## 提供商兼容

按 [DeepSeek Chat Completions 文档](https://api-docs.deepseek.com/api/create-chat-completion/) 接入正式函数调用。本轮主模型关闭思考，因此请求 `tool_choice=required`；DeepSeek 思考开启或未明确关闭时使用 `auto`，避免该组合的 HTTP 400。思考内容仅用于必要的工具对话续接，不作为代码正确性的证据。

保留旧 JSON 文本模式以兼容其他网关。`single` 工作流仍走旧文本接口，本轮改造面向五角色工作流。

## 自动化验证

完整套件 **120 项通过**，新增检查包括：原生请求参数与调用 ID 对应、多动作不执行但完整反馈所有调用 ID、补充测试隔离、失败检查不能被新检查覆盖、旧 revision 不能复用结果、检测测试执行时修改副本、一次纠正不突破共享预算、缺少补充验证不能接受、失败检查否决接受申请、批量编辑全部校验后写入、保留 Windows 换行、开发交接仍须测试通过。

## 有界真实验证

首批共四次：发票 hybrid、零边界 hybrid、流式 dynamic 和 hybrid。随后针对发现的兼容问题修正，再跑流式 dynamic、hybrid 各一次。两次均卡在 Developer 回合上限，因此补充批量编辑与开发交接机制，最后各跑一次，总计八次并停止追加实验。每阶段分别记录，不合并成单版本成功率。每次上限维持 8192 输出 token、12 个角色回合、64 次总调用、16 步、600 秒，没有因失败提高数值预算。

首批记录：

- `runs/structured-validation/eval-20260929-143302-30e1b854`：发票与零边界均完整通过（2/2），实际执行补充验证；普通 JSON 协议错误为 0。
- `runs/structured-validation/eval-20260929-143401-d02d85d8`：流式两次均失败（0/2）。dynamic 被提供商意外返回的多个函数调用中断；hybrid 的补丁独立验收通过，但生成的补充测试存在错误断言，Reviewer 反复尝试接受，耗尽上下文。两次失败保留，没有替换为后续结果。
- 修正后复测：`runs/structured-followup/eval-20260929-144240-43b5d16f`。
- 最后交接验证：`runs/structured-handoff/eval-20260929-144843-a62496e8`。

兼容修正后的两次流式结果为 0/2：dynamic 多次修复后仍在 Developer 回合耗尽，独立验收收集失败；hybrid 已生成独立验收通过的补丁，但同样未完成 Developer 提交。这是增加“交给 Tester 实测”的直接依据，不是放宽最终成功标准。

最后阶段结果仍为 **0/2**：dynamic 用完 64 次模型调用，独立验收失败；hybrid 在 52 次调用后触发本地上下文上限，独立验收也失败。Hybrid 曾在公开测试通过后进入 Reviewer，补充检查发现闭引号后空格的处理遗漏并拒绝接受；后续保留的检查也包含模型自认的错误诊断断言，程序与测试的语义分歧仍未解决。不能把所有补充检查失败都当成真实程序缺陷。

最后两次实际运行没有触发 Developer 回合耗尽交接事件；该机制有自动化测试覆盖，但尚无本轮真实运行成功证据。首阶段普通案例通过发生在后续兼容和交接修改之前，不能当作最终代码的完整真实回归。

## 记录核对与结论

四个批次各保存 `audit.json` 和 `recovery_summary.json`。核对确认：运行组合无缺失或重复、案例内容指纹一致、原仓库与受保护测试未改变、角色/路由/轻量模型 token 分项相加一致；两条成功记录的公开测试、Reviewer 和补充检查对应同一 revision。运行文本产物未发现本地配置的 API 密钥。最后批次代码指纹与当前源码一致；前三批保留各自历史版本指纹，与最终源码不同是阶段修改所致。

本轮解决了一部分协议和工具使用问题，并增加了阻止错误接受的验证门禁，但**没有解决复杂案例成功率问题**。剩余主要障碍是多轮修改中的逻辑错误和无效编辑、模型生成测试本身不可靠，以及反复诊断造成上下文与调用预算耗尽。不能用增加预算或删掉失败检查来宣称修复。

本轮八次真实调用任务已结束，不再追加实验。若继续优化，应先从已保存的失败轨迹做离线定位，确定如何依据原始需求区分错误测试与错误补丁，再另行开展固定版本的有界评测；当前结果不足以断言换模型或启用思考就一定改善。
