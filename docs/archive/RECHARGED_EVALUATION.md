## 运行中发现的限制与诊断计划

流式案例的部分 DeepSeek 响应返回空正文，usage 显示 `completion_tokens=4096` 且 `reasoning_tokens=4096`。因此这些失败发生在生成可执行动作之前，不是测试失败后的调度失败。官方文档说明 Flash 默认支持思考模式，输出长度受 `max_tokens` 限制：[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)、[API 参数](https://api-docs.deepseek.com/api/create-chat-completion/)。客户端本轮未保存 `finish_reason`，不能从产物直接断言该字段的值。

另建 `configs/streaming-diagnostic.json`，仅把单次输出上限从 4096 提到 8192、每角色回合从 8 提到 12；其他预算与模型保持一致。额外运行 Hybrid 两次，验证较充分预算下能否进入真实测试与恢复流程。诊断结果单独报告，不与原配置比较表混合。不是成功率基准，不以得到成功结果为停止条件。

`12_atomic_transfers` 的外部验收要求未知账户抛 `KeyError`，而 issue 只要求拒绝未知账户，没有明确异常类型。原实现的字典访问隐含该异常，但验收约束未充分写明；因此相关外部验收失败保留，同时标为规格歧义，不能直接用来证明某策略修复能力较差。运行期间不修改该案例或评分规则。

**真实 Debugger 纠错仍未获得证据。** 本轮全部 25 次运行，实际 Tester 失败次数为 0，Debugger 调用次数为 0。到达 Tester 的补丁一次通过公开测试；其余失败发生在模型动作协议、预算或事后外部验收阶段。现有模拟测试仍是 Debugger 路径的主要验证，不能以这次压力测试声称真实模型已跑通失败恢复。

这不是要求模型先犯错的理由。下一步应先解决可观测的模型接入问题：记录响应结束原因，区分输出截断与普通 JSON 错误，显式配置思考模式，并改善多动作响应的提示与回合使用；然后在明确规格的任务上继续观察自然失败。接口与协议修改需要新版本和新批次，不应回改本轮结果。
